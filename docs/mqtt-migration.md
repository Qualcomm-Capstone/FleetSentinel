# FleetSentinel: 수집 정책 변경과 gRPC → MQTT 전환

**평상시에는 필요한 상태만 준실시간으로 전송하고, 이상 상황이나 집중 관찰 때 특정 차량의 필요한 신호를 더 자주 전송한다. 이 수집 정책과 차량별 명령 전달을 구현하는 경로로 MQTT를 선택했다.**

이 문서는 세 가지 질문에 답한다.

1. 기존 설계와 무엇이 달라졌는가?
2. 그 변화가 왜 MQTT 선택으로 이어졌는가?
3. MQTT로 바꾸면서 무엇을 추가로 고려해야 하는가?

현재 구현은 기존 gRPC와 병행할 수 있는 **로컬 검증 단계**다. 클라우드 배포나 차량 1,000~10,000대 수용량을 검증한 상태는 아니다. 정책·저장 확인·명령의 상세 조건은 [MQTT 수집 계약](mqtt-contract.md)에 정리했다.

## 1. 기존 설계와 무엇이 달라졌는가?

### 1.1 전량 전송에서 상황·센서별 선택적 전송으로 변경

기존 설계는 차량에서 발생하는 신호·객체 메타데이터를 지속적으로 서버에 전달하고, 클라우드에서 이상을 탐지하는 데 초점을 맞췄다. 전송 중 유실을 막기 위해 차량의 WAL과 서버의 저장 확인인 CACK도 구현했다.

재검토한 지점은 **모든 센서의 모든 샘플을 평상시에도 계속 클라우드로 보내야 하는가**였다. 위치·임무 상태와 고주파 IMU 이력은 용도가 다르고, 평상시 관제와 사고 대응도 같은 전송 빈도가 필요하지 않다.

| 구분 | 기존 경로 | 변경한 방향 |
|---|---|---|
| 평상시 | 신호·객체 메타데이터를 지속 전송 | 선택한 상태 신호를 변화량·최대 보고 간격에 따라 전송 |
| 집중 관찰 | 상황별 전송 정책이 없음 | 선택 차량·선택 채널의 빈도를 일정 시간 높임 |
| 상세 센서 이력 | 발생 데이터를 클라우드로 전달 | 차량에 보관하고, 사건·요청 구간을 선택해 업로드 |
| 관제자의 개입 | 수집·저장 확인이 중심 | 정책 변경·이력 요청·진단 명령과 적용 결과 확인 |
| 유실 방지 대상 | 전송 대상으로 기록한 데이터 | **업로드 대상으로 선택해 영속 기록한 데이터** |

차량 내부의 센서 수집률을 일괄적으로 낮추는 것은 아니다. **로컬 기록과 클라우드 전송을 분리**하는 것이다. 보존 기간이 지난 비선택 이력의 삭제는 정책에 따른 삭제이고, 업로드 대상으로 보존한 데이터가 저장 확인 없이 사라지는 것은 유실이다.

카메라·라이다 원본은 별도다. 원본을 MQTT에 싣지 않으며, 기존 presigned HTTPS 파일 업로드와 gRPC 업로드 제어 API를 유지한다. 사건 시 원본 요청과 자동 보존·삭제 정책 전체가 이번에 구현된 것은 아니다.

### 1.2 전송 정책 변경에 따른 처리량 감소와 비용 절감 범위

다음은 차량 1,000대가 같은 크기의 상태 레코드를 보낸다는 가정으로 계산한 **보고 간격별 전송량 예시**다.

| 가정 | 클라우드에 보내는 상태 레코드 수 |
|---|---:|
| 모든 차량이 1초마다 1건 전송 | 1,000건/초 |
| 평상시 모든 차량이 10초마다 1건 전송 | 평균 100건/초 |
| 990대는 10초마다, 집중 관찰 10대는 1초마다 전송 | 평균 109건/초 |

마지막 조건에서는 레코드 수가 첫 번째보다 **89.1% 감소**한다. 이 감소는 gRPC에서도 동일한 선택 정책을 적용하면 얻을 수 있다. 실제로는 변화량 보고·이상 이벤트·이력 업로드·재전송이 추가되므로, 이 비율을 전체 트래픽이나 클라우드 요금 절감률로 사용하면 안 된다.

여기서 **배칭과 데이터 선택도 구분**해야 한다. 10개 샘플을 한 배치에 넣으면 전송 메시지 수는 줄지만, 서버가 저장·연산할 샘플은 여전히 10개다. 평상시 필요한 샘플만 선택해야 클라우드의 레코드 처리량과 적재량까지 줄어든다.

### 1.3 전송 빈도 감소에 따른 탐지 지연과 정책 조정

10초 간격으로 받는 데이터를 가지고 이전과 같은 1초 단위 탐지를 보장할 수는 없다. 따라서 평시에도 최초 이상 발견에 필요한 상태 신호는 유지하고, 더 빠른 대응이 필요한 판단은 차량에서 수행할지 정해야 한다.

현재 구현은 선택한 상태 신호의 클라우드 탐지와 외부 차량 판단기의 이상 입력을 받아 동작한다. 새로운 차량 이상 탐지 알고리즘을 구현한 것은 아니다. 보고 간격·임계치·허용 지연은 실제 업무 요구사항으로 확정해야 한다.

## 2. 그렇다면 왜 gRPC에서 MQTT로 바꾸는가?

### 2.1 gRPC에서도 구현 가능한 선택적 전송·배칭·양방향 통신

gRPC에서도 선택적 전송, 배칭, 양방향 스트리밍, 애플리케이션 ACK를 구현할 수 있다. 양방향 스트림으로 차량에 명령을 전달하는 것도 가능하다. [gRPC 공식 문서](https://grpc.io/docs/what-is-grpc/core-concepts/)

프로토콜 비교의 기준은 변경된 요구사항을 구현하고 운영할 때 각 기능을 어디서 담당할지다.

### 2.2 MQTT 선택 근거: 차량별 메시지 라우팅과 세션 관리

차량은 상태 데이터를 전송하고 관제 명령을 수신한다. 관제자는 특정 차량에 “30초 동안 더 자주 보고하라”, “이 구간의 이력을 보내라”는 명령을 보내고, 적용 결과도 확인해야 한다. 차량의 연결 단절과 재접속도 고려해야 한다.

이때 직접 구현할 범위를 비교했다.

| 필요한 기능 | gRPC를 유지한다면 | MQTT를 사용하면 |
|---|---|---|
| 특정 차량으로 명령 전달 | 차량이 연결된 게이트웨이를 찾고 해당 스트림으로 전달하는 구조가 필요 | 차량별 토픽을 구독하게 하고 브로커가 메시지를 전달 |
| 재접속 이후 통신 재개 | 스트림 재생성·애플리케이션 수준의 구독/전달 상태 복원을 설계 | 세션·구독·QoS 기능을 활용하되 만료·영속성 설정은 필요 |
| 차량 연결과 Kafka 적재 처리의 분리 | 게이트웨이와 별도의 메시지 라우팅 계층 등을 구성 가능 | 브로커가 차량 연결을 받고 bridge가 구독해 Kafka로 적재 |
| 최종 저장·명령 적용 확인 | 애플리케이션 로직 필요 | **여전히 애플리케이션 로직 필요** |

MQTT는 토픽 기반 publish/subscribe와 세션 기능을 제공한다. 다만 재접속 시 보존 범위는 세션 만료·QoS·서버 설정 등에 따라 달라지며, 영구적인 업무 상태 저장을 대신하지 않는다. [MQTT 5.0 표준](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html)

**MQTT를 선택해 차량별 비동기 메시지 전달과 세션 관리를 브로커에 맡긴다.** 애플리케이션은 수집 정책·저장 확인·명령 적용을 담당한다.

### 2.3 MQTT 도입에 따른 브로커 운영 부담과 gRPC 유지 대안

MQTT를 도입하면 브로커가 추가된다. 연결·세션·구독 상태를 보관할 자원, 장애 복구, 인증서·토픽 권한 관리가 필요하며 메시지가 거치는 단계도 늘어난다.

따라서 MQTT가 항상 더 빠르거나 저렴하다고 결론 내리지 않는다. 차량의 통신망·TLS 재연결·keepalive·로컬 디스크 기록 비용까지 포함한 전력 및 비용 비교는 아직 필요하다. 현재 JSON 전송 봉투의 base64 인코딩은 Avro 바이너리보다 본문 크기를 약 33% 늘린다는 점도 측정에 포함해야 한다.

반대로 상향 수집이 대부분이고 안정적인 연결 환경이라면, **기존 gRPC를 유지하면서 수집 정책만 바꾸는 선택도 유효**하다. 이번 선택의 우선순위는 단순한 전송 성능 우위보다 차량별 메시지·명령 운영 구조에 있다.

### 2.4 기존 처리량·배칭·확장성 판단의 정정

초기 gRPC 선정 근거 중 다음 판단을 정정했다. 기존 검토 원문은 Git 이력에 남아 있다.

| 초기 판단 | 정정한 내용 |
|---|---|
| MQTT로 약 1,295 rec/s를 처리할 수 없다 | in-flight 20, 특정 RTT, 레코드당 PUBLISH 1개를 가정한 계산이었다. 실제 비교에는 전송 정책·배치 크기·브로커 설정·통신 환경을 반영해야 한다 |
| 애플리케이션 배칭은 축적 시간만큼 유실 위험을 만든다 | 영속화 전 메모리 축적이 유실 위험을 만든다. 현재는 outbox에 먼저 기록한 뒤 배치를 구성한다 |
| 배치 전송이면 중복 제거도 배치 단위여야 한다 | 전송·ACK은 배치 단위, Kafka 기록·중복 처리는 레코드 단위로 구분한다 |
| 브로커가 추가되므로 MQTT의 신뢰성이 낮다 | 장애 지점 수만으로 신뢰성을 비교할 수 없다. 로컬 보존·저장 확인·재전송·장애 복구 범위를 함께 검증해야 한다 |
| gRPC 게이트웨이는 stateless라 자동으로 확장된다 | 복구 상태를 차량에 두어도 활성 연결과 차량별 명령 라우팅은 별도 설계가 필요하다. MQTT도 브로커 세션·큐 분산과 복구를 설계해야 한다 |

## 3. MQTT로 바꾸면서 무엇을 고려해야 하는가?

데이터 경로에는 MQTT 브로커와 bridge가 들어간다. bridge는 MQTT 메시지를 받아 Kafka에 기록하는 수집 서비스다.

```text
기존: 차량 WAL    → gRPC 게이트웨이             → Kafka → Flink
변경: 차량 outbox → MQTT 브로커 → 수집 bridge → Kafka → Flink
```

### 3.1 MQTT PUBACK과 Kafka 저장 확인용 application ACK의 분리

차량이 MQTT PUBACK을 받았다는 이유로 로컬 데이터를 삭제하면 안 된다. 브로커가 받은 뒤 bridge나 Kafka 단계에서 문제가 발생할 수 있기 때문이다.

새 경로도 기존 WAL+CACK의 원칙을 유지한다. **저장 확인이 오기 전까지 차량이 원본을 보존한다.**

1. 차량이 전송할 데이터를 로컬 outbox에 영속 기록한다.
2. MQTT로 발행하고, bridge가 배치 안의 모든 레코드를 Kafka에 쓴다.
3. Kafka 쓰기가 모두 성공하면 bridge가 application ACK를 보낸다.
4. 차량이 배치 ID와 시퀀스 범위를 확인한 뒤 해당 outbox 데이터만 삭제한다.

여기서 확인하는 지점은 **Kafka 저장**이다. ClickHouse 반영 완료까지 확인하는 것은 아니다. MQTT의 QoS만으로 전체 파이프라인의 저장 완료를 보장한다고 설명하지 않는다. [MQTT 5.0 QoS 규정](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html)

### 3.2 로컬 이력과 전송 대기 데이터의 보존·삭제 정책

로컬 저장소를 두 역할로 구분했다.

| 저장소 | 목적 | 삭제 조건 |
|---|---|---|
| ring buffer | 최근 상세 이력 보관과 업로드할 구간 선택 | 비선택 이력은 기간·용량 상한에 따라 삭제. 선택한 이력은 outbox로 옮길 때까지 고정 |
| durable outbox | 업로드 대상으로 선택한 데이터의 재전송 | 해당 배치의 application ACK를 받은 뒤 삭제 |

새 경로는 SQLite WAL을 사용해 outbox·시퀀스·명령 처리를 트랜잭션으로 기록한다. 기존 gRPC WAL 파일을 그대로 재사용하거나 자동 변환하는 방식은 아니다.

outbox가 가득 차면 CLI는 새 입력 처리를 대기시키고 전송·ACK·명령 처리를 계속한다. 공간이 생기면 대기 입력을 재시도한다. 수용 전 입력은 메모리에 있으므로 프로세스 종료에 대비한 원천 어댑터의 보존·재공급은 별도로 필요하다.

### 3.3 상태·이벤트·이력별 시퀀스와 ACK 범위 분리

상태(`status`), 이상 이벤트(`event`), 상세 이력(`history`)의 시퀀스와 저장 확인 범위를 분리했다. 과거 이력의 ACK가 늦다고 긴급 이벤트의 로컬 보존 해제까지 기다리게 하지 않기 위해서다.

각 stream의 배치는 최대 128건·64 KiB로 제한하고, 재전송에서도 같은 배치 ID를 사용한다. Kafka에 일부만 기록됐거나 ACK가 유실되면 중복 전송이 생길 수 있으므로 Flink·ClickHouse에서도 같은 데이터의 식별자가 유지돼야 한다.

이는 큐와 ACK의 논리적 분리다. 같은 통신망·브로커 자원을 사용하므로 긴급 이벤트의 지연 시간이 자동으로 보장되는 것은 아니다.

### 3.4 하행 명령의 적용 확인·중복 실행 방지·만료 처리

“집중 관찰 명령을 발행했다”와 “차량이 보고 주기를 바꿨다”는 다르다. 그래서 서버의 요청 상태(desired)와 차량의 적용 결과(reported)를 따로 기록한다.

명령 ID는 중복 실행을 막고, 정책 버전은 오래된 설정으로 되돌아가는 것을 막는다. 만료 시간은 연결 복구 뒤 이미 지난 명령이 실행되는 것을 막는다. 집중 관찰도 유효기간이 지나면 정상 주기로 복귀한다.

관제자의 집중 관찰과 이상 에피소드의 유지 시간은 분리한다. 직접 관찰 중 발생한 첫 이상도 이력을 선택하고, 둘 중 하나라도 유효하면 집중 관찰 주기를 유지한다. 잘못된 정책 명령은 거절하고 수집·전송은 계속한다.

현재는 운영자 CLI로 요청·결과를 처리한다. 관제 UI/API의 사용자별 권한·감사와 공유 DB 기반 운영은 남아 있다.

### 3.5 보고 간격·발생 시각을 반영한 경보 및 최신 상태 조회

| 그대로 두면 생기는 문제 | 변경한 처리 |
|---|---|
| 10초마다 정상 보고하는 차량을 5초 뒤 통신 장애로 판단 | 보고 간격을 반영한 미수신 기준 사용 |
| 과거 이력을 새 이상 상황으로 탐지 | history를 현재 경보 판단에서 제외 |
| 늦게 도착한 과거 위치가 지도 위치에 반영 | 발생 시각을 기준으로 최신 위치 선택 |
| 서로 다른 stream의 같은 시퀀스를 중복으로 판단 | stream·boot 단위 식별과 중복 제거 |

현재 미수신 기준은 기존 설정과 `보고 간격 × 3` 중 큰 값이다. 이 배수는 구현 기본값이며 실제 운영 기준으로 확정된 값은 아니다. 센서와 클라우드의 시계 동기화도 필요하다.

### 3.6 브로커·bridge의 확장 책임과 인증·접근 제어

브로커는 차량 연결·세션·구독을 담당하고, bridge는 메시지 검증과 Kafka 적재를 담당한다. shared subscription으로 bridge 간 처리를 분산할 수 있지만, **MQTT 브로커 자체가 stateless가 되는 것은 아니다.**

브로커의 HA·세션 복구, bridge 처리 용량, Kafka·Flink의 처리량을 각각 계획해야 한다. 특히 모든 차량의 동시 재접속과 집중 관찰 차량 증가가 별도의 부하 시나리오다.

차량 인증서에는 자신에게 허용된 토픽만 사용할 권한을 부여한다. 현재 개발 설정은 인증서 CN을 세션 신원으로 사용하므로 bridge 복제 시에도 인스턴스별 인증서·권한이 필요하다. 단일 개발 브로커와 인증서 하나를 복제하는 것으로 운영 HA가 완성되지는 않는다.

## 4. 어디까지 바뀌었고, 무엇이 남았는가?

**구현·검증한 범위:** 선택적 수집, 만료되는 고빈도 모드, 로컬 보존과 application ACK, 차량 명령/결과, MQTT→Kafka 적재, 지연 이력을 고려한 Flink·조회 처리다. 재전송·브로커 재시작·토픽 접근 제어 등은 로컬 자동 테스트로 확인했다.

**운영 전에 남은 범위:** 클라우드 HA, 관제 UI/API 권한과 감사, 실제 차량 센서 어댑터, 원본 MCAP 자동 보존·삭제, 대규모 연결·무선망·전력·비용 측정이다. 따라서 이번 구현을 운영 전환 완료로 해석하면 안 된다.

기존 gRPC와 원본 업로드 경로, Kafka 복제·ACK 정책은 유지했다. 새 경로를 적용할 때는 **MQTT 입력보다 먼저 하류 Flink를 변경**해야 하며, 기존 WAL과 새 outbox를 섞어 읽거나 동일 데이터를 양쪽 경로에 동시에 보내지 않는다.

정책·저장 확인·명령은 [MQTT 수집 계약](mqtt-contract.md), 적용·롤백은 [SDD §5](sdd.md)에 정리했다.
